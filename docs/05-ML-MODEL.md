# The Recovery-Propensity Model

> One number — P(this recovery attempt collects) — and an honest account of where it comes
> from.

The model is the smallest component in the system and the easiest one to oversell. This
document does the opposite: it states what the number means, states plainly that the ground
truth behind it is synthetic, writes out the generative process so the assumptions can be
argued with, and reports the measured results including the baseline that the model has to
beat.

Everything below is read from `backend/app/ml/` and `backend/models/metrics.json`.

---

## 1. What it predicts, and where the number goes

**Target.** Binary: `recovered = 1` when a recovery attempt collects the money from the
customer. The model outputs the probability of that, in `[0, 1]`.

It is scored **per candidate strategy**, not per payment. The same failed payment produces a
different score for "retry the same card" than for "switch this customer to UPI", and that
difference is the entire product thesis expressed as a number.

The score is persisted on the case (`propensity_score`, `propensity_model_version`) and
written to the audit trail as a `propensity_scored` entry. Four consumers act on it:

| Consumer | What it does with the score |
|---|---|
| `score_recovery_propensity` (agent tool) | A read-only tool. The agent calls it once per strategy it is considering and cites the result in its rationale. |
| `plan_from_rules` (no-LLM planner) | Below `LOW_PROPENSITY_ESCALATION_FLOOR = 0.10` it escalates to a human instead of proposing an attempt. |
| `R10_PROPENSITY_FLOOR` (guardrail) | Denies the case when the score is below `settings.min_propensity_score = 0.15`. |
| `PropensityGauge` (approval screen) | Renders the score, its `model_version`, its drivers, and a loud badge when the number came from the fallback heuristic. |

Two properties of that wiring matter more than the model itself:

- **The amount is not a tool parameter.** `score_recovery_propensity` takes the failure
  category, the proposed strategy and optionally the method and attempt number. The amount
  is read from the pinned payment row. If the agent could vary the amount it could probe
  "what if this were smaller?" and then write a rationale built on a number that is not the
  real one.
- **R10 can only subtract permission, never add it.** A high score approves nothing. One
  other rule reads the score — R13's low-risk auto-approval lane, which requires
  `auto_approve_min_propensity = 0.80` — but that lane ships off (`auto_approve_enabled =
  false`), so in the demo every rupee still needs a human click. A miscalibrated or fallback
  score can therefore only make the system *more* conservative, which is the correct
  direction for a model trained on data like this.

## 2. The data is synthetic

**The training data is generated by `backend/app/ml/dataset.py`. It is not real Razorpay
data and it is not sampled from any public dataset.** That belongs at the top of this
document because it is the single most important fact about every metric below it.

No payment processor publishes "we retried N failed payments of category X with strategy Y
and Z% collected" — recovery performance is commercially sensitive. A merchant's own
transaction history is precisely the asset that will not be handed to a student project. So
there were three honest options:

1. Ship no model and score propensity with an if/else ladder.
2. Copy plausible-looking rates from a blog post and present them as fact.
3. Write the generative process down as executable, commented code so a reviewer can audit
   the assumptions instead of taking a number on faith.

Option 3 is what shipped. Every probability in the next section is a stated belief about how
Indian payment failures behave, with the reasoning attached, and each one is a single edit
away from being replaced by a merchant's real numbers.

**What that costs the metrics.** A 0.8023 ROC-AUC measured on data you generated is a
measurement of your generator. It says the pipeline learns the structure that was put into
the data, that the preprocessing is sound, and that the ensemble extracts more signal than a
shallow tree does. It says nothing about Indian payment recovery. The learned model is a
compression of the assumptions in section 3 and is worth exactly as much as they are. The
feature engineering, the pipeline, the baseline comparison and the threshold choice are
real work and would transfer unchanged to real merchant data; the ground truth would not.

## 3. The generative process

Six terms multiply to produce the probability of a successful recovery. Multiplication
rather than addition, because each of these can independently kill the attempt: a perfect
strategy on a dead instrument still collects nothing, and an additive model would let a
strong customer history rescue an impossible case.

```
p = CATEGORY_BASE_RATE[category]
  * STRATEGY_FIT[category, strategy]
  * amount_factor(amount)
  * ATTEMPT_FACTOR[attempt_number]
  * customer_quality_factor(latent_quality)
  * time_factor(hours_since_failure)
```

clamped into `[MIN_PROBABILITY, MAX_PROBABILITY]` = `[0.01, 0.97]`, because nothing in
payments is ever certain in either direction.

### 3.1 Category base rates

`CATEGORY_BASE_RATE` is the probability that a *typical* attempt — first try, average
customer, average amount — collects. It is the category's centre of gravity, not its
ceiling; the strategy multipliers move it up and down from there.

The bands, and the reasoning that assigns each category to one:

| Band | Meaning |
|---|---|
| ~0.75 | Nothing was wrong with the customer or the instrument. The payment failed on our side of the fence. |
| ~0.60 | Intent existed but the window closed. |
| ~0.45 | The customer hit a step they could not complete. |
| ~0.20–0.32 | A real constraint blocked the payment — the issuer said no, the money was not there, the card is dead. |
| ~0.02 | We must not try. |

| Category | Base rate | Why it sits there |
|---|---|---|
| `gateway_error` | **0.75** | Razorpay or the acquirer faulted. Customer did nothing wrong, instrument is fine. |
| `network_error` | **0.74** | Same transient character; marginally lower because a dropped connection can hide a genuine decline that never reached us. |
| `upi_timeout` | **0.62** | The collect request expired unanswered. Usually the customer did not open the app in time; some are silent refusals. |
| `session_expired` | **0.58** | Checkout window closed. Intent was real, but time has passed and some of it has cooled. |
| `authentication_failed` | **0.45** | OTP or 3-D Secure not completed. A coin-flip: some mistyped, some never received it. |
| `bank_decline` | **0.32** | The issuer refused. What recovery exists comes almost entirely from switching rails. |
| `customer_abandoned` | **0.30** | No technical fault to fix. This is a persuasion problem. |
| `unknown` | **0.25** | Unclassified. Set at the rough population average — absence of evidence is not evidence of failure. (It is also not evidence of safety, which is why R3 blocks it anyway.) |
| `insufficient_funds` | **0.22** | No money in the account. Retrying now cannot work by definition. |
| `invalid_instrument` | **0.18** | Expired or mistyped card. Anything reusing the instrument is wasted. |
| `risk_blocked` | **0.02** | Near zero on purpose: a "successful" recovery here is plausibly a chargeback in three weeks. R3 excludes these before the model is consulted; the near-zero rate exists so that if the guardrail were removed, the model would still refuse on its own. |

### 3.2 Strategy fit

`STRATEGY_FIT` is the product thesis in numeric form: the right recovery action depends on
*why* the payment failed. Above 1.0 beats the category average; below 1.0 wastes the
attempt. If every cell were 1.0, the product would have no reason to exist.

| Category | `retry_same_method` | `retry_later` | `switch_to_upi` | `switch_to_card` | `switch_to_netbanking` |
|---|---|---|---|---|---|
| `bank_decline` | 0.55 | 0.75 | **1.25** | 0.70 | 1.10 |
| `insufficient_funds` | 0.60 | **1.35** | 0.80 | 0.95 | 0.70 |
| `upi_timeout` | **1.20** | 0.80 | **1.20** | 0.85 | 0.75 |
| `session_expired` | **1.25** | 0.70 | 1.05 | 1.00 | 0.95 |
| `gateway_error` | **1.20** | 0.90 | 1.00 | 0.95 | 0.90 |
| `network_error` | **1.20** | 0.90 | 1.00 | 0.95 | 0.90 |
| `authentication_failed` | 0.90 | 0.70 | **1.30** | 0.70 | 0.80 |
| `invalid_instrument` | 0.25 | 0.35 | **1.40** | 1.10 | 1.20 |
| `customer_abandoned` | 1.00 | 0.90 | **1.20** | 0.85 | 0.75 |
| `unknown` | 0.95 | 0.85 | 0.95 | 0.90 | 0.90 |
| `risk_blocked` | 0.30 | 0.30 | 0.30 | 0.30 | 0.30 |

Reading a few rows out loud: re-presenting a card the issuer just refused scores 0.55, while
moving that customer to UPI scores 1.25, because UPI runs a different authorisation path and
the issuer's card-side decision does not follow it there. Re-presenting a dead card scores
0.25 — the clearest bad fit in the table, and the one the model most needs to learn.
`insufficient_funds` is the only row where waiting wins (1.35), which is the reason
`RETRY_LATER` exists as a strategy at all. `risk_blocked` is deliberately flat: keeping it
uniform avoids implying that some clever rail choice makes a fraud-flagged transaction
collectable.

Two strategies create no payment attempt at all and are applied to every category:
`manual_review` = **0.10** and `no_recovery` = **0.02**. They are not zero — a human operator
occasionally rescues a payment off-platform, and a customer very occasionally returns
unprompted. Hard zeros would let the model treat "recommend manual review" as a guaranteed
negative and learn to recognise the *recommendation* rather than the situation. An
untabulated pair falls back to `DEFAULT_STRATEGY_FIT = 0.85`, neutral-but-pessimistic, so a
forgotten table entry degrades a score rather than flattering an untested combination.

### 3.3 The continuous adjustments

| Term | Definition | Reasoning |
|---|---|---|
| Attempt | `ATTEMPT_FACTOR = {1: 1.00, 2: 0.62, 3: 0.40}`, `0.30` beyond | The drop from first to second attempt is steep on purpose: the first attempt already harvested the easy transient failures, so what remains is structurally harder. This is also the quantitative argument behind `max_recovery_attempts = 2`. |
| Customer | `0.65 + 0.70 × success_rate` | Linear and centred so a customer with no history — reported as the neutral 0.5, matching `Customer.prior_success_rate` — gets exactly 1.0 and is neither rewarded nor punished for being new. Range roughly 0.65 to 1.35. |
| Amount | `1.05 − 0.075 × log10(rupees / 100)`, clamped to `[0.80, 1.05]` | Larger payments hit issuer velocity limits, exhaust balances and prompt hesitation. Logarithmic, not linear: the gap between ₹100 and ₹1,000 matters far more than the gap between ₹40,000 and ₹41,000. |
| Time | `0.55 + 0.45 × exp(−hours / 36)` | Intent is perishable. The decay halves the distance to the floor roughly every 25 hours. It decays *to a floor*, not to zero, because a small share of customers do come back a week later. |

Customer histories are drawn with a deliberate gap between what is true and what is
observable. Each synthetic customer has a hidden quality `q ~ Beta(5, 3)` (mean ≈ 0.63); the
feature row sees only the *observed* success rate from `Binomial(total_payments, q)`, while
the outcome is driven by `q`. That gap is what makes `customer_total_payments` a real
feature rather than a decorative one: 1-out-of-1 and 40-out-of-40 report the same rate and
carry completely different amounts of evidence, and the correct response is to shrink a thin
history back towards the population mean. That shrinkage is an interaction between two
numeric features — the kind of structure a tree ensemble can represent and a logistic
regression cannot.

The population mix is stated rather than left to a uniform draw, because it sets the class
balance and therefore every reported metric. It is shaped like an Indian mid-market
checkout: `bank_decline` 0.20, `upi_timeout` 0.15, `insufficient_funds` 0.13,
`authentication_failed` 0.11, `session_expired` 0.10, `gateway_error` 0.08, `network_error`
0.07, `customer_abandoned` 0.06, `invalid_instrument` 0.06, `risk_blocked` 0.02, `unknown`
0.02. Attempt numbers are drawn `{1: 0.75, 2: 0.20, 3: 0.05}`. Payment method is drawn
*conditionally* on the category — a collect request only exists on UPI, OTP failures are a
card and netbanking phenomenon — because drawing it independently would put impossible rows
like "UPI timeout on a netbanking payment" into training and waste model capacity on a
correlation reality already guarantees.

### 3.4 Why the labels are drawn, not thresholded

The generator computes `p` and then draws the label with `rng.random() < p`.

The alternative — labelling `p > 0.5` as a success — would make the mapping from features to
label a pure deterministic function, which a gradient-boosted tree can memorise almost
perfectly. The resulting ~0.99 ROC-AUC would be a measurement of the threshold, not of the
model, and it would be worthless. Bernoulli sampling produces a learnable but irreducibly
noisy signal, so the reported metrics mean what metrics normally mean.

On top of that, an unobserved multiplier `LogNormal(0, LATENT_NOISE_SIGMA = 0.12)` is applied
before the draw. It stands for everything the feature row cannot see: the issuer's policy
that morning, whether the customer's phone had signal, whether their spouse said no. It puts
a genuine ceiling below 1.0 on any achievable score, which is the honest situation for this
problem.

## 4. Distribution coverage, and the bug it prevented

This is the section worth reading twice, because it is where the generator stopped being a
convenience and started being a modelling decision. Three of its parameters exist because
the naive version of each produced a model that was measurably, specifically wrong — and in
two of the three cases the error was invisible in ROC-AUC.

### 4.1 `PLAYBOOK_SAMPLING_RATE = 0.45` — counterfactual coverage

45% of generated rows carry the best strategy for their category; the rest are drawn
uniformly across all seven strategies.

That number looks too exploratory for a distribution meant to resemble production, and it is
— deliberately. **The model is queried counterfactually.** The predictor is never asked "will
this recovery, drawn from the deployed policy, succeed?". It is asked "how likely is *this*
strategy for *this* failure", once per candidate, including strategies the playbook would
never choose. A logging policy that almost always follows the playbook cannot answer that
question, because the interesting cells are nearly empty.

Sampling only the best strategy would mirror deployment but leave the model no
counterfactual evidence — it would never once see "retry the same dead card" and so could
never learn that it fails. Sampling uniformly would give perfect coverage and a training
distribution that looks nothing like production. The mixture buys coverage of the bad
choices while keeping the good ones dominant, which is the trade-off an exploration rate
makes in a bandit.

**The bug.** At a sampling rate of 0.70, the `bank_decline × retry_same_method` cell held
about 50 rows out of 6,000. The model could not separate that interaction from the strong
global association between "retry the same method" and the easy transient categories
(`gateway_error`, `network_error`, `session_expired`, all of which favour a same-rail
retry). It therefore scored **re-presenting a declined card above switching the customer to
UPI** — precisely the wasted retry this whole system exists to prevent, asserted by the
product's own ML, on the same screen as the playbook recommendation saying the opposite.

The broken model scored 0.78 ROC-AUC and looked perfectly healthy. Aggregate ranking quality
is blind to a wrong ordering inside a rare cell.

Raising exploration and the sample count fixed the ordering **and**, measured over five
seeds, raised held-out ROC-AUC from 0.782 to 0.809 while tightening its variance. Better
coverage generalised better, so there was no accuracy/validity trade-off to make.
`tests/test_ml_predictor.py` now pins six category → (better strategy, worse strategy)
orderings, so this cannot regress silently.

### 4.2 Amount — a two-component mixture, not a single log-normal

Real transaction values are log-normal in shape: a dense mass of everyday purchases with a
long tail of expensive ones. But a single log-normal centred on the everyday mass leaves the
tail with almost no support — at a median of ₹600 with sigma 1.0, fewer than two rows in
18,000 land above ₹24,000.

That matters here specifically, because **the amounts this model is queried on are not
distributed like the amounts it would be trained on.** The guardrail thresholds sit at
₹10,000 (`high_value_review_threshold_paise`, R5) and ₹50,000
(`max_recovery_amount_paise`, R4) — so the cases a human actually looks at are concentrated
exactly where a single log-normal has no data. A gradient-boosted tree asked to extrapolate
there returns whatever its last split happened to say. It did: it scored a ₹24,000 failure
well above a ₹199 one, inverting the documented relationship.

The fix is a mixture. `HIGH_VALUE_SHARE = 0.18` of rows are drawn from a second component
with a median around ₹9,900; the rest from the everyday component with a median around ₹600.
The high-value band stays a minority of transactions, as it should be, but a well-populated
one.

### 4.3 Age — a mixture whose components overlap on purpose

Same failure, same fix, one extra subtlety.

A plain exponential is the honest shape for *when recovery decisions get made* — most within
a few hours — but it puts effectively no mass beyond five days. R11 permits recovery up to
`max_payment_age_hours = 168`, and the seeded demo spreads failures across a fortnight, so
the model was being asked about a region containing essentially no training data. It
extrapolated, and got the **sign** wrong: a five-day-old failure scored *higher* than an
hour-old one, exactly reversing the intent decay the generator documents.

`BACKLOG_SHARE = 0.35` of rows are now drawn uniformly across the window instead. That
component represents a real population anyway — failures that sat in a queue over a weekend
before anyone looked at them.

The uniform component spans the **whole** 0–168 hour window rather than starting where the
exponential thins out. An earlier version started it at 24 hours, which put a step change in
the density at exactly that point. The trees found the step and split on it, and the learned
response picked up a bump at 24 hours that nothing in the ground truth justifies. Overlapping
the components removes the artefact: a boundary the generator does not smooth over is a
boundary the trees will happily learn.

## 5. Features

Nine columns. `FEATURE_COLUMNS` fixes their order, and both training and serving build rows
through the same function.

| Column | Type | Meaning |
|---|---|---|
| `failure_category` | categorical (one-hot) | Classified reason the original payment failed. One of eleven `FailureCategory` values. |
| `payment_method` | categorical (one-hot) | Instrument the original payment used. `unknown` is a real, trained-on token, not a gap. |
| `proposed_strategy` | categorical (one-hot) | The recovery strategy being evaluated. One of seven. This is what makes the query counterfactual. |
| `amount_rupees` | numeric | `amount_paise / 100`. Rupees purely as a modelling scale — paise would sit two orders of magnitude above every other numeric column. No value derived here is ever written back to a payment, an order or a ledger entry; the authoritative amount stays integer paise everywhere it matters. |
| `attempt_number` | numeric | 1 for the first recovery attempt on this case. |
| `customer_prior_success_rate` | numeric | Share of the customer's past payments that succeeded. A customer with no history is 0.5, the same neutral prior the ORM returns. |
| `customer_total_payments` | numeric | How many payments that rate is computed from — how much the rate can be trusted. |
| `hours_since_failure` | numeric | Age of the original failure. |
| `is_same_method_retry` | numeric, derived 0/1 | 1 when the proposed strategy re-presents the payment on the same rail. |

**On the derived flag.** `is_same_method_retry` is 1 for `retry_same_method`, 1 for
`retry_later` (retrying later is still the same rail; only the clock changes), 1 for a
`switch_to_X` whose target rail is the one the payment already used, and 0 for
`manual_review` and `no_recovery`, which create no payment at all. It exists because "retry
the same method" means something completely different depending on why the payment failed:
re-presenting an expired card is hopeless, re-sending a UPI collect request the customer
simply missed is close to free money. The model can express that only by spending one-hot
combinations on it, so the interaction is handed over pre-computed. It does not appear in the
top twelve importances below, which is consistent with the strategy and method one-hots
carrying most of the same information — but it costs one column and makes the three-way
interaction available to a shallow tree directly.

**No training/serving skew, structurally.** There is exactly one function in the codebase
that turns raw payment facts into a model row — `build_feature_row` in
`backend/app/ml/features.py` — and both the synthetic generator and the live predictor call
it. The classic way a working model silently rots is the training script deriving
`amount_rupees` one way and the API deriving it another; here a feature definition changes in
one place and both sides move together. `features.py` also has no third-party imports, so it
can be imported and tested without pandas or scikit-learn present.

Column *order* is part of the contract too. The `ColumnTransformer` selects by name, but the
one-row DataFrame the predictor builds is constructed with `columns=FEATURE_COLUMNS`, so a
fitted artefact can never be handed columns in an order it was not fitted on.

## 6. Model and evaluation

### The pipeline

```
ColumnTransformer
  ├── OneHotEncoder(handle_unknown="ignore", sparse_output=False) → 3 categorical columns
  └── StandardScaler()                                            → 6 numeric columns
        ↓
GradientBoostingClassifier(
    n_estimators=250,
    learning_rate=0.08,
    max_depth=4,
    subsample=0.9,
)
```

Preprocessing and classifier live inside one `Pipeline`, so the fitted encoder and scaler
travel with the model in the same `.joblib` file. Pickling the estimator alone and
re-deriving the encoding at inference is the single most common way a deployed model starts
scoring garbage, because nothing then forces the serving-side encoding to match the
training-side one.

Scaling is not required by a tree ensemble. It is there because the same transformer feeds
the decision-tree baseline and would feed a linear model if one were added, and an unscaled
`amount_rupees` next to `customer_prior_success_rate` is a trap waiting for whoever adds it.

**Why 250 shallow trees at a low learning rate.** Many small corrections generalise better on
a noisy label than a few aggressive ones, and this label is noisy by construction (§3.4).

**Why `max_depth=4`, not 3.** The interaction the model exists to represent is three-way:
failure category × proposed strategy × whether that strategy reuses the failed instrument.
Depth 3 could not hold it against the much stronger *marginal* effect of the strategy alone —
and the symptom was the ordering bug in §4.1, a model that rated re-presenting a declined
card above switching rails. Depth was raised together with the exploration rate in
`dataset.py`; neither alone was sufficient. Measured across five seeds, the pair fixed 24 of
25 playbook orderings without costing held-out ROC-AUC. Depth 5 was tried and rejected: no
ordering improvement, and the train/test gap started widening, which on a Bernoulli label
means fitting noise.

### The baseline

`DecisionTreeClassifier(max_depth=5)` is trained on the identical preprocessing step and
reported alongside, every run. A single shallow tree is the right baseline because it is
roughly what a sensible engineer would write by hand — a nested if/else over failure category
and attempt number — so beating it is the minimum bar for the extra dependency and the extra
opacity an ensemble costs. Reporting both means the model choice is evidenced rather than
asserted, and if the baseline ever wins, that is a result worth acting on.

### Results

`v1-gradient_boosting-18000`, seed 42. 18,000 rows, stratified 80/20 split — 14,400 train,
3,600 test. Positive rate 0.316.

| Metric @ threshold 0.5 | GradientBoosting | DecisionTree (d=5) |
|---|---|---|
| accuracy | **0.7547** | 0.7281 |
| precision | **0.6564** | 0.6256 |
| recall | **0.4701** | 0.3480 |
| f1 | **0.5479** | 0.4472 |
| **roc_auc** | **0.8023** | 0.7293 |

The ensemble earns its place against that baseline: +0.073 ROC-AUC and +0.122 recall over
the hand-writable one.

### The harsher baseline: does the model beat the table it learned from?

A shallow tree is the wrong thing to be reassured by here, because it is still a *trained*
model. The comparison that actually matters on synthetic data is against the generating
process itself — two dictionary lookups multiplied together, no training at all:

```python
CATEGORY_BASE_RATE[category] * STRATEGY_FIT[(category, strategy)]
```

Scored on the identical held-out rows, and printed by `python dev.py train` on every run so
the number cannot drift from the artefact:

| Scorer | ROC-AUC |
|---|---|
| Untrained lookup table (two lines) | 0.7827 |
| **Trained GradientBoosting** | **0.8023** |
| Noise-free generating function (the ceiling) | ~0.809 |

**The model is worth +0.0196 ROC-AUC over two dictionary lookups**, and that closes roughly
four-fifths of the distance to the theoretical ceiling. What it is buying is the part the
table cannot express: the attempt-number decay, the recency decay, and the customer-history
effect. What it is *not* buying is insight into payments — it is re-deriving, imperfectly,
assumptions that are written down twenty lines away.

That is the honest ceiling of what synthetic data can demonstrate about a model, and it is
stated here rather than left for a reviewer to work out. Two things follow from it, and both
are the point:

- **On this data, the table is a legitimate answer.** If the gain fell below the bar in
  `train.py` (`MIN_WORTHWHILE_GAIN`), the trainer says so in as many words and the right
  call would be to ship the table and delete the dependency.
- **On real data there is no table.** A merchant's recovery outcomes are not generated from
  anything; the base rates would have to be *learned*, which is exactly what this pipeline
  does. The feature engineering, the leakage-free split, the counterfactual coverage work in
  §4 and the operating-point choice in §7 are the parts that transfer. The trained artefact
  is the part that does not.

**5-fold cross-validated ROC-AUC: 0.7933 ± 0.0067.** Stratified, and run on the *training
split only* — cross-validating on the full dataset would let the held-out test set influence
model selection, which quietly turns the final numbers into training-set numbers. The
cross-validated mean sitting a little below the single held-out score, with a standard
deviation under 0.01, is what a model that is not overfitting its split looks like.

ROC-AUC is the number used for model selection here because it is threshold-free: the
operating threshold is a policy decision made in `config.py`, so the model should be chosen
on its ranking quality rather than on its behaviour at an arbitrary cut point.

Confusion matrix at 0.5 (n = 3,600):

## 7. The operating point

Choosing a classifier means choosing which mistake you would rather make, and that choice
belongs to the domain, not to the library. Here the two mistakes are wildly asymmetric:

- **False positive** — we predict a recovery would succeed, we attempt it, it fails. Cost:
  one gateway API call (effectively free) and a small amount of customer friction, itself
  already bounded by R1 (at most two attempts), R2 (a 15-minute cooldown) and R8 (at most
  three cases per customer per day).
- **False negative** — we predict the recovery is hopeless, never attempt it, and a payment
  that would have collected is written off. Cost: the **entire transaction value**,
  permanently, plus the customer relationship attached to it.

A false negative is worth many false positives, so the operating point is pushed towards
recall. Concretely, `min_propensity_score = 0.15`, not the reflexive 0.5. Its only job is to
screen out the genuinely hopeless — risk-blocked transactions, dead instruments being
re-presented, third attempts on a stale case. Everything with a pulse reaches a human, who is
far better placed than a synthetic-data model to make the marginal call.

Measured at that floor, on the same held-out 3,600 cases:

| At `min_propensity_score = 0.15` | |
|---|---|
| recall | **0.9525** |
| precision | **0.4198** |
| screened out | **1,018** of 3,600 test cases |

Read that as the trade it is. 2,582 cases pass the floor; about 1,084 of the 1,138 real
positives survive, and roughly 54 are lost. Precision falls from 0.6564 to 0.4198 — well over
half of what passes will not collect — and that is the intended purchase. The gateway calls
are cheap; the 54 written-off transactions are not, and at a 0.5 threshold that number would
be 603.

Reporting both thresholds is deliberate. The 0.5 metrics in §6 are the conventional
reporting point, comparable to any other binary classifier. The 0.15 numbers are what the
system actually runs on. The training script reads the floor from `config.py` rather than
hard-coding it, so the reported number cannot drift away from the limit the guardrail
enforces.

**On the medical-screening comparison.** This is the same *shape* of reasoning as a screening
classifier, where a missed diagnosis costs incomparably more than a false alarm and recall is
bought with precision. It is not the same argument. There the asymmetry comes from harm to a
patient; here it comes from the arithmetic of a gateway call versus a lost transaction. The
direction has to be re-derived from this domain's costs rather than assumed — it happens to
land the same way. If the economics were reversed, say each attempt cost the merchant a
chargeback fee, the correct floor would be far higher, and the right response would be to
change `min_propensity_score` in the config, not to retrain anything.

## 8. Known limits

**The response near the top of the age range is noisy.** Two things compound. The true effect
is nearly flat there — `time_factor` decays towards a floor of 0.55 with a 36-hour constant,
so by the back half of the 168-hour window the exponential term is all but exhausted and the
ground truth barely moves. And the data is thinner: past a few days only the 35% uniform
backlog component contributes, so each hour carries a fraction of the rows the first hours
carry. A flat signal measured on fewer samples is a noisy signal, and the learned response in
that region should not be read as a finding. `hours_since_failure` is nonetheless the single
most important feature, because the part of the curve that *is* steep — the first day or two —
is where most of the data lives.

**The amount effect is genuinely weak, and correspondingly weak in the model.** Across the
entire permitted range, ₹100 to ₹50,000, the amount multiplier falls only from 1.05 to about
0.85; the lower clamp of 0.80 is never reached inside the range the guardrails allow. The
ground truth simply does not make amount a strong driver, and the model agrees — 0.0737
importance, sixth. This is worth stating because a reviewer might reasonably expect amount to
matter more, and because §4.2 describes going to some trouble to fix the amount
*distribution*. That work fixed a sign error in a weak effect. It did not make the effect
strong, and no amount of modelling could have.

**Everything above is worth exactly what §3 is worth.** The metrics measure how well a
gradient-boosted ensemble recovers a structure that was deliberately put into the data. If
`CATEGORY_BASE_RATE` is wrong about Indian issuers, or `STRATEGY_FIT` is wrong about UPI
taking a different authorisation path, then the model is confidently wrong in exactly the
same way, and no metric in this document would show it. The mitigations are structural rather
than statistical: the assumptions are readable and editable in one file, the orderings the
product asserts out loud are pinned by tests, and R10 lets the score subtract permission but
never add it.

## 9. Retraining

```bash
python dev.py train                              # the normal path
python -m app.ml.train                           # equivalent, from backend/
python -m app.ml.train --samples 30000 --seed 7  # a different run
```

On Windows, substitute `dev.bat` for `python dev.py`. `python dev.py demo` runs setup, seed
and train in sequence.

A run generates the data, fits both models, cross-validates on the training split, scores
everything once on the held-out set, prints an ASCII report, and writes two files into
`backend/models/`:

| File | Contents |
|---|---|
| `propensity_model.joblib` | The fitted `Pipeline` — encoder, scaler and classifier together — with the version string stamped onto the object itself. |
| `metrics.json` | Everything in §6 and §7, plus `trained_at`, `seed`, `n_samples` and the confusion matrix. |

The version is stamped onto the artefact rather than only written to the JSON because "which
model produced this score?" is an audit question. `metrics.json` is a separate file that can
be deleted, replaced or copied from another run; a value carried inside the pickle cannot be
separated from the model it describes. The predictor prefers the stamp and falls back to the
JSON.

The whole run is reproducible: one seed drives the data generator, the split and both
classifiers, and `numpy.random.default_rng(seed)` gives a fresh, independent bit generator
rather than mutating global numpy state, so the same seed produces byte-identical data on
Windows, macOS and Linux.

### When the artefact is missing

**The application runs without it.** Clone, install, start — every screen works, the
propensity column is populated, and R10 has a number to compare against. `predict()` never
raises: a missing file, a pickle written by a different scikit-learn version, a corrupt
artefact, a feature dict with a key spelled wrong — every one of them degrades to a documented
heuristic. A model artefact is not permitted to take down a payment flow.

The heuristic is `CATEGORY_BASE_RATE × attempt_factor × customer_quality_factor`, clamped to
`[0.02, 0.95]`. It reuses those multipliers straight from `dataset.py`, so the fallback is a
coarse version of the model rather than a second, contradictory opinion. It deliberately
stops at two adjustments — strategy fit, amount and recency all belong in the real model, and
folding them in here would make the heuristic look like a model and invite people to trust it
as one.

**A degraded score is labelled, never disguised.** `PropensityResultOut.is_fallback` is
`true`, `model_version` reads `heuristic-v1` — a shape deliberately unlike a trained version
string so nobody skim-reading a case row confuses the two — and both travel through the API to
the approval screen, which swaps the model-version badge for a "Heuristic estimate" warning
and a note telling the operator to read the number as an ordering hint between cases rather
than as a calibrated probability. `GET /api/status` reports `ml_model_loaded` and
`ml_model_version` for the same reason, and
the app's mode banner surfaces it globally. A demo that quietly falls back and shows the same
confident number either way is lying to its user.

Because loading is deferred to first use, a training run that finishes while the API is
already up is picked up by the next process without any special handling.
