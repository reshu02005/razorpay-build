# API Reference

The backend serves a single REST API at **`http://127.0.0.1:8000`**. Every route lives
under `/api`, every response is JSON, and there is no authentication: the server binds to
the loopback interface and is meant to be run on the reviewer's own machine.

Interactive documentation is generated by FastAPI from the same Pydantic schemas the code
uses, and is always in sync with the running build:

| URL | What it is |
|---|---|
| `http://127.0.0.1:8000/docs` | Swagger UI — every endpoint, every field, executable in the browser |
| `http://127.0.0.1:8000/redoc` | The same specification, rendered for reading |
| `http://127.0.0.1:8000/openapi.json` | The raw OpenAPI document |

This file is the narrative companion to those pages. `/docs` can tell you that
`POST /api/recovery/cases/{case_id}/approve` accepts an `approved_by` string; it cannot
tell you that the guardrails are evaluated a second time inside that call, that a `403` is
therefore an ordinary outcome rather than a bug, or which call to make next. That is what
follows.

Browser clients are subject to CORS. The allowed origins default to
`http://localhost:3000`, `http://127.0.0.1:3000` and `http://localhost:3001` — the third
because Next.js silently moves to 3001 when 3000 is occupied. Change the list with
`CORS_ORIGINS` in `backend/.env`.

## The error envelope

Every non-2xx response has the same three-field shape, `ErrorOut`:

```json
{
  "error": "guardrail_denied",
  "message": "Denied by 1 rule: customer already has 3 recovery cases today; the daily limit is 3.",
  "detail": {
    "case_id": "case_b9c35e4eaa774ac3",
    "blocking_rules": ["R8_CUSTOMER_VELOCITY"],
    "status": "blocked"
  }
}
```

* `error` — a stable machine token. It is part of the API contract and will not change.
* `message` — prose for a human. It may be reworded at any time.
* `detail` — optional structured context, or `null`. Its keys vary by error code and are
  described per endpoint below.

**Branch on `error`, never on `message`.** The message is written for an operator reading a
screen; matching substrings against it produces a client that breaks the first time
somebody improves the wording. The frontend in `frontend/src` follows this rule and so
should any other consumer.

The uniformity is deliberate. Three exception handlers in `app/main.py` cover everything the
application produces: the whole domain error hierarchy, FastAPI's own validation failures,
and Starlette's framework-level errors such as a 404 for an unknown path. A client therefore
parses errors in exactly one place, including for the mistyped URLs a developer makes while
learning the API.

### Stable error codes

| `error` | HTTP | Meaning |
|---|---|---|
| `not_found` | 404 | A referenced payment, customer, case, order or named scenario does not exist. |
| `invalid_signature` | 400 | An HMAC on a checkout callback or a webhook did not verify. The payload is not authentic, so it is never acted on. |
| `guardrail_denied` | 403 | The policy engine refused the action. `detail.blocking_rules` lists the `rule_id`s that returned DENY. |
| `approval_required` | 403 | A money-moving step was reached on a case that no human has approved. |
| `duplicate_case` | 409 | A recovery case already exists for this payment — either still in flight or already closed. |
| `invalid_transition` | 409 | The requested move is not an edge in the recovery state machine, or the payment is not in `failed` status. |
| `gateway_error` | 502 | Razorpay (or the simulator standing in for it) failed or answered unusably. The fault is upstream; a retry may succeed. |
| `configuration_error` | 500 | The application is configured in a way that cannot work — for example simulated checkout requested while real Razorpay keys are live. |
| `validation_error` | 422 | The request body or query string failed schema validation. `detail.errors` carries Pydantic's per-field list. |
| `http_error` | varies | A framework-level failure: unknown path, wrong method. `detail.status_code` repeats the status. |
| `internal_error` | 500 | The base error class's own code. No endpoint raises it today; it exists so that a new failure type cannot accidentally ship without a code. |

A genuine bug — a `KeyError`, a driver timeout — is not in this table and is not rendered as
an `ErrorOut`. There is no catch-all handler, deliberately: an unexpected fault surfaces as
the ASGI server's plain 500 and a stack trace in the console, rather than being dressed up
as a known outcome.

A *missing* credential is never a `configuration_error`. Running with no Gemini key and no
Razorpay keys is a supported mode, reported by `GET /api/status`, not an error.

## Conventions

**Money.** Every amount is an integer in paise, in a field ending `_paise`. A rounded rupee
convenience field sits alongside it (`amount_paise: 115600`, `amount_rupees: 1156.0`). The
rupee value is for display only; nothing in the system computes with it.

**Time.** All timestamps in typed fields are ISO-8601 UTC ending in `Z`, for example
`2026-08-29T20:10:55.166883Z`. Timestamps nested inside an audit event's opaque `payload`
object are whatever the writing code serialised and may use `+00:00` instead.

**Identifiers.** Application ids are a prefix plus 16 hex characters: `cust_`, `pay_`,
`case_`, `att_` (recovery attempt), `evt_` (audit event), `tc_` (tool call), `run_` (one
agent analysis run, which groups the tool calls it produced). Gateway ids
follow Razorpay's shape — `order_` or `pay_` plus 14 upper-case alphanumerics — in both real
and simulated mode, so nothing downstream can accidentally depend on the difference.

**Request bodies are required.** Endpoints that declare a body require one even when every
field in it is optional. `POST /api/payments/simulate-failure` with no body is a `422`; send
`{}`. The same applies to `analyze` and `mark-failed`.

**Unknown body fields are rejected.** Every request schema sets `extra="forbid"`, so a typo
in a field name is a `422` rather than a silently ignored key.

**curl on Windows.** Windows 10 and 11 ship `curl.exe`. In PowerShell, `curl` is an alias
for `Invoke-WebRequest`, so type `curl.exe` explicitly. The examples below quote JSON as
`-d "{\"key\":\"value\"}"`, which works from `cmd.exe`; on macOS or Linux the more familiar
`-d '{"key":"value"}'` is equivalent. Single quotes are *not* string delimiters on
`cmd.exe`, so the escaped form is the portable one.

## System

### `GET /api/health`

Liveness probe. Returns `{"status": "ok"}` and performs no I/O at all — no database session,
no gateway call, no model load.

That restraint is the point. A health check that touches its dependencies conflates "should
this process be restarted?" with "is the system fully functional?", and would report
unhealthy while the app is running correctly in its documented zero-credential mode.

**Response** `200` — `{"status": "ok"}`

---

### `GET /api/status`

The app's self-report: which reasoning engine, which gateway, which model. Read this first.
It is the single source of truth behind the start-up banner and the UI header, so a demo
cannot quietly imply it is doing something it is not.

**Response** `200` — `SystemStatusOut`

```bash
curl http://127.0.0.1:8000/api/status
```

```json
{
  "app": "RecoverAI",
  "version": "1.0.0",
  "environment": "development",
  "agent_mode": "rule_based",
  "gemini_model": null,
  "gateway_mode": "simulated",
  "ml_model_loaded": true,
  "ml_model_version": "v1-gradient_boosting-18000",
  "database": "sqlite (recoverai.db)",
  "warnings": []
}
```

| Field | Notes |
|---|---|
| `agent_mode` | `llm` or `rule_based`. Answers "which code produced the recommendations in this database?" |
| `gemini_model` | The model name when `agent_mode` is `llm`, otherwise `null`. |
| `gateway_mode` | `razorpay_test` or `simulated`. |
| `ml_model_loaded` | `false` means the trained artefact is absent and the documented heuristic is scoring instead. |
| `database` | Dialect and, for SQLite, the filename. The DSN itself is never published. |
| `warnings` | Only conditions the typed fields cannot express — an interpreter outside the tested range, or a Gemini key that is set but unusable. Degraded modes are *not* repeated here as prose. |

## Metrics

### `GET /api/metrics/dashboard`

Every headline figure the landing dashboard shows, in one call. Volumes and the failure rate
are measured over original payments only (`is_recovery_attempt = false`), so one customer's
single intention to pay is never counted twice.

An empty database reports zeroes rather than failing: "0% of nothing" is an honest answer,
and a `ZeroDivisionError` rendered as a 500 would leave a reviewer unable to tell an empty
system from a broken one.

**Response** `200` — `DashboardMetricsOut`

```bash
curl http://127.0.0.1:8000/api/metrics/dashboard
```

  money we failed to recover, so counting it would understate the system against a target it
  was never allowed to aim at.
* `daily_budget_used_paise` against `daily_budget_limit_paise` is R7 in progress: the total
  value of recovery orders created today versus the blast-radius cap.

### `GET /api/metrics/failure-breakdown`

Count, volume and recovered count per failure category, busiest first. This is the evidence
for the project's central claim — that the right recovery action differs by failure reason,
so the reasons have to be counted separately.

Measured over recovery **cases**, not payments, because a category only exists once a
payment has been classified. Failures nobody has analysed yet are absent here on purpose;
they are reported as `unanalysed_failures` on the dashboard, where "we have not looked at
these" reads as the call to action it is instead of hiding inside an `unknown` slice.

**Response** `200` — `list[FailureBreakdownItem]`

```json
[
  {
    "category": "authentication_failed",
    "count": 1,
    "volume_paise": 115600,
    "volume_rupees": 1156.0,
    "recovered_count": 1
  }
]
```

### `POST /api/payments/simulate-failure`

Manufactures a realistic failed payment from the seeded scenario catalogue. It exists
because a reviewer cannot make a real card decline on demand.

It is not a shortcut around the pipeline. The row it writes is an ordinary `Payment`
carrying the gateway's real error vocabulary, and the analysis, guardrail and approval path
that follows is the same one a Razorpay webhook would trigger. The customer's
`total_payments` counter is incremented, because a failed attempt is still an attempt in
that customer's history.

**Request** — `SimulateFailureIn`. Every field is optional; omitted fields are drawn from a
randomly chosen catalogue scenario and a randomly chosen seeded customer.

| Field | Type | Notes |
|---|---|---|
| `customer_id` | string | Must exist; otherwise `404`. |
| `amount_paise` | integer, 100–100 000 000 | Overrides the generated amount. |
| `method` | `card` \| `upi` \| `netbanking` \| `wallet` \| `emi` \| `unknown` | Overrides the scenario's instrument. |
| `scenario` | string | A key from the catalogue, e.g. `insufficient_funds_upi`. |
| `description` | string, ≤ 255 chars | |

The eighteen catalogue keys are `bank_decline_card`, `bank_decline_netbanking`,
`card_expired`, `checkout_session_expired`, `customer_cancelled_upi`,
`gateway_technical_error`, `incorrect_otp`, `insufficient_funds_card`,
`insufficient_funds_upi`, `international_card_blocked`, `invalid_card_number`,
`invalid_vpa`, `issuer_down`, `network_timeout`, `suspected_fraud`,
`unclassified_failure`, `upi_collect_expired`, `upi_payment_pending_timeout`. There is no
endpoint that lists them, because an unknown name returns them in `detail.available`.

**Response** `201` — `PaymentOut`
**Errors** `404 not_found` (unknown scenario or customer), `500 configuration_error` (no
customers seeded — run `python dev.py seed`), `422 validation_error`

```bash
curl -X POST http://127.0.0.1:8000/api/payments/simulate-failure ^
```

## Recovery

This group is the product. One failed payment becomes one recovery case, and the case moves
through the state machine in `app/domain/enums.py`.

### `POST /api/recovery/payments/{payment_id}/analyze`

Runs the agent, scores propensity, evaluates all thirteen guardrails, and persists one
recovery case with the complete reasoning trace. **No money moves here** and no order is
created; the furthest this call can advance a case is to "waiting for a human to say yes".

**Request** — `AnalyzeIn`

| Field | Type | Default | Notes |
|---|---|---|---|
| `force_rule_based` | boolean | `false` | Forces the deterministic planner even when a Gemini key is configured. Useful for showing the degraded path. |

**Response** `201` — `RecoveryCaseOut`, with `status` routed to one of:

| `status` | When |
|---|---|
| `awaiting_approval` | The strategy moves money and no rule denied it. |
| `blocked` | A guardrail returned DENY. Terminal. |
| `no_action` | The agent chose `no_recovery` or `retry_later` — doing nothing is the right answer. Terminal. |
| `escalated` | The agent chose `manual_review`. A human must handle it off-platform. Terminal. |

Note what this endpoint does **not** return: a `403`. A proposal-time refusal is a
successful analysis whose conclusion is "no", so it is a `201` carrying
`status: "blocked"` and `guardrail_decision: "deny"`.

**Errors** `404 not_found`, `409 invalid_transition` (the payment is not `failed`),
`409 duplicate_case`, `422 validation_error`

Re-analysing a payment whose case is in `failed` re-proposes onto the **same** case, which
is what carries `attempt_count` forward. A case in any other non-terminal state, or in a
terminal state, is a `duplicate_case` conflict.

```bash
curl -X POST http://127.0.0.1:8000/api/recovery/payments/pay_e584a6bf7d594366/analyze ^
```

verdict. Computing that in React would fork the guardrails into a second copy that drifts —
and the copy a user can see is not the copy that guards the money.

### `GET /api/recovery/cases/{case_id}/trace`

The agent's reasoning, one row per tool call, oldest first. A re-analysed case has more than
one run and all of them are returned; `run_id` groups them, so "why did it decide
differently the second time?" is answerable.

The `capability` column is the point of this endpoint. It lets a reader confirm from the
data — not just from the code — that no money-moving tool was ever in the loop. Values are
`read_only`, `write_proposal` and `financial`; the last never appears, and a test fails the
build if a financial tool is ever registered for the agent.

### `POST /api/recovery/cases/{case_id}/approve`

The only path in the system that causes money to move, and it requires a named human.

The order of operations is the product: confirm the case is still awaiting approval,
**re-evaluate every guardrail against live state**, record the approval with a name
attached, create the attempt under the deterministic idempotency key
`case_id:attempt_number`, ask the gateway for an order for the amount on the *payment*,
publish the recovery link, and commit once.

**Request** — `ApproveIn`

| Field | Type | Required | Notes |

### `POST /api/recovery/cases/{case_id}/verify`

The endpoint Razorpay Checkout's success handler posts to. The HMAC-SHA256 signature over
`"<order_id>|<payment_id>"` is recomputed server-side **before anything is written**.

A browser callback is a claim, not proof: the client posts "payment succeeded" from
JavaScript an attacker fully controls. Without server-side verification, marking any case
recovered would be one curl command with a guessed case id, and the merchant's dashboard
would report money that was never collected.

The order is also required to belong to *this* case. The signature covers only the id pair,
so a genuinely signed pair from a different case would verify perfectly well; binding the
callback to an order this case created is what stops one customer's valid receipt from
closing someone else's case.

**Request** — `VerifyPaymentIn`

| Field | Type | Required |
|---|---|---|
| `razorpay_order_id` | string, 1–64 chars | yes |
| `razorpay_payment_id` | string, 1–64 chars | yes |
| `razorpay_signature` | string, 1–256 chars | yes |

**Response** `200` — `RecoveryCaseOut` with `status: "recovered"`. A new `Payment` row is
written with `is_recovery_attempt: true` and `parent_payment_id` pointing at the original,
the customer's counters and lifetime value move, and the case gains `recovered_at` and
`recovered_amount_paise`.

**Errors**

| Status | `error` | When |
|---|---|---|
| `400` | `invalid_signature` | The HMAC did not match. The rejection is recorded and the case is deliberately left in `awaiting_payment` — a forged callback must not close a live case, and the real customer may still pay. |
| `404` | `not_found` | The order id does not belong to this case. |
| `409` | `invalid_transition` | The case has no payment outstanding. |

```json
{
  "error": "invalid_signature",
  "message": "Payment signature verification failed. This payment has not been accepted.",
  "detail": {
    "case_id": "case_328ea80b6b6e47ce",
    "order_id": "order_RWNTKIHA0RZE2S"
  }
}
```

Note the absence of an amount field in the request. The recovered amount is taken from the
case, which took it from the original payment; the callback is never allowed to name a
number.

### `POST /api/recovery/cases/{case_id}/mark-failed`

Forces the live attempt to fail, so the failure branch of the state machine can be
demonstrated without waiting for a real abandonment.

**Request** — `MarkAttemptFailedIn`

### `GET /api/audit/verify`

Recomputes the SHA-256 of every event in sequence order and compares it with the stored
hash. This is what turns the immutability claim from a sentence in a README into something a
reviewer can check.

Three independent properties are tested, because tampering takes three shapes: content
integrity (an edited row), linkage (a spliced or reordered row) and gaplessness (a deleted
row — the first two alone would not catch a deletion, since removing the last event leaves a
perfectly self-consistent chain). Verification stops at the first break, and `head_hash` is
`null` in that case: a chain with a hole in it has no head anyone should rely on.

**Response** `200` — `AuditChainVerificationOut`

```bash
curl http://127.0.0.1:8000/api/audit/verify
```

```json
{
  "valid": true,
  "events_checked": 26,
  "head_hash": "bd5c9b4bc194698fa125ee59dd1abc7ea4fb434422f5a0deabb4dd28faf13651",
  "broken_at_sequence": null,
  "message": "Audit chain intact: 26 event(s) verified from genesis to sequence 26."
}
```

A tampered ledger answers `valid: false` with `broken_at_sequence` naming the first failing
row. An empty ledger is vacuously valid — reporting a fresh install as compromised is both
wrong and the kind of false alarm that trains people to ignore the real one.

## Webhooks

### `POST /api/webhooks/razorpay`

Receives Razorpay webhook deliveries. This is the one endpoint an unauthenticated stranger
can reach, so three rules govern it.

**The raw bytes are read before anything else.** Razorpay signs the exact body it
transmitted; parsing to a dict and re-serialising changes key order, whitespace and unicode
escaping, so the HMAC would never match. The handler calls `request.body()`, verifies, and
only then parses.

**An event we do not handle still gets a 200.** Razorpay retries any non-2xx response with
backoff, so returning an error for `payment.captured` would schedule repeated redeliveries
of an event we deliberately ignore. `400` is reserved for the one case where a retry is
genuinely the right thing to demand: a body whose signature does not verify.

**Every delivery is written to the ledger**, handled or not. "We never received it" and "we
received it and chose not to act" are different statements, and only one of them is
defensible after the fact.

**Headers**

| Name | Notes |
|---|---|
| `X-Razorpay-Signature` | HMAC-SHA256 of the raw body, keyed with `RAZORPAY_WEBHOOK_SECRET`. |

**Body** — the raw Razorpay event. Only `payment.failed` is acted on; the payment entity is
read from `payload.payment.entity` and flattened into a new failed `Payment`. An unknown
email creates a customer, because a merchant frequently meets a customer for the first time
through a failed payment. Every lookup is defensive: a malformed body is acknowledged and
recorded rather than raising, since a 500 here would become a retry storm.

**Response** `200` — `{"received": true}`
**Errors** `400 invalid_signature` — only when a webhook secret is configured and
verification fails.

With no `RAZORPAY_WEBHOOK_SECRET` set, the delivery is processed but the audit payload
records `"signature_verified": false`, so nobody later mistakes the row for authenticated
input. The server also logs a warning.

```bash
curl -X POST http://127.0.0.1:8000/api/webhooks/razorpay ^
  -H "Content-Type: application/json" ^
  -H "X-Razorpay-Signature: <hmac-sha256-of-the-raw-body>" ^
  -d "{\"event\":\"payment.failed\",\"payload\":{\"payment\":{\"entity\":{\"id\":\"pay_QsA1bC2dE3fG4h\",\"order_id\":\"order_QsZ9yX8wV7uT6s\",\"amount\":249900,\"currency\":\"INR\",\"method\":\"upi\",\"email\":\"asha.iyer@example.in\",\"contact\":\"+919812300003\",\"error_code\":\"BAD_REQUEST_ERROR\",\"error_source\":\"customer\",\"error_step\":\"payment_authentication\",\"error_reason\":\"payment_timed_out\",\"error_description\":\"The UPI collect request expired before the customer approved it.\"}}}}"
```

```json
{ "received": true }
```

The resulting ledger entry:

```json

  "actor_type": "webhook",
  "actor_id": "razorpay",
  "summary": "Razorpay webhook 'payment.failed' received and ingested",
  "payload": {
    "body_bytes": 445,
```

## The recovery lifecycle as an API sequence

This is the exact call order that takes one failed payment from analysis to recovered, with
the state of the system after each call. Every id below comes from the previous response.

**0. Have a failed payment.** Either seed the database (`python dev.py seed`) and pick one
from `GET /api/payments?status=failed`, or manufacture one:

```bash
curl -X POST http://127.0.0.1:8000/api/payments/simulate-failure ^
  -H "Content-Type: application/json" -d "{}"
```

> *State:* a `Payment` with `status: "failed"` and `recovery_case_id: null`. The customer's
> `total_payments` counter has moved. One `payment_failed` audit event exists.

**1. Analyse it.**

```bash
curl -X POST http://127.0.0.1:8000/api/recovery/payments/pay_e584a6bf7d594366/analyze ^
  -H "Content-Type: application/json" -d "{}"
```

> *State:* one `RecoveryCase` exists, `status: "awaiting_approval"`, `attempt_count: 0`,
> `can_approve: true`. The failure is classified, propensity is scored, all thirteen
> guardrails are evaluated and frozen onto the case together with the policy snapshot. Five
> or six audit events are appended (`analysis_started`, `failure_classified`,
> `propensity_scored`, `strategy_proposed`, `guardrails_evaluated`, `approval_requested`).
> **No order exists and no money has moved.**
>
> If the verdict was DENY the status is `blocked` instead and the sequence ends here. If the
> agent recommended `no_recovery` or `retry_later` the status is `no_action`; if it
> recommended `manual_review` it is `escalated`. All three are terminal, and all three still
> return `201`.

**2. Read the case and, if you want, the reasoning.**

```bash
curl http://127.0.0.1:8000/api/recovery/cases/case_45af48a0f7a64c4a
curl http://127.0.0.1:8000/api/recovery/cases/case_45af48a0f7a64c4a/trace
```

> *State:* unchanged. Both are pure reads.

**3. Approve — the only money-moving call.**

```bash
curl -X POST http://127.0.0.1:8000/api/recovery/cases/case_45af48a0f7a64c4a/approve ^
  -H "Content-Type: application/json" -d "{\"approved_by\":\"priya@merchant.in\"}"
```

> *State:* the guardrails have been re-evaluated against live state and the new verdict has
> replaced the old one on the case. The case walked `approved` → `executing` →
> `awaiting_payment` in one transaction. `attempt_count` is `1`, a `RecoveryAttempt` row
> exists under the idempotency key `case_id:1` carrying a `razorpay_order_id`, and
> `expires_at` is set 60 minutes out. `approval_granted`, `guardrails_evaluated`,
> `recovery_order_created` and `recovery_link_sent` are in the ledger.
>
> A `403 guardrail_denied` here moves the case to `blocked` and ends the sequence. That is
> the system working, not failing.

**4. Fetch the checkout session** (this is what the customer's recovery page loads).

```bash
curl http://127.0.0.1:8000/api/recovery/cases/case_45af48a0f7a64c4a/checkout
```

> *State:* unchanged. You now have `order_id`, the amount, and `razorpay_key_id` — `null` in
> simulated mode.

**5a. Simulated gateway — play the customer.**

```bash
curl -X POST "http://127.0.0.1:8000/api/recovery/cases/case_45af48a0f7a64c4a/simulate-checkout?succeed=true"
```

**5b. Real Razorpay Test Mode** — Checkout's success handler posts the three fields it
returns:

```bash
curl -X POST http://127.0.0.1:8000/api/recovery/cases/case_45af48a0f7a64c4a/verify ^
  -H "Content-Type: application/json" ^
  -d "{\"razorpay_order_id\":\"order_...\",\"razorpay_payment_id\":\"pay_...\",\"razorpay_signature\":\"...\"}"
```

Both go through the same server-side verification; 5a simply mints the signature first.

> *State:* the case is `recovered`, with `recovered_at` and `recovered_amount_paise` set. A
> second `Payment` row exists with `is_recovery_attempt: true` and `parent_payment_id`
> pointing at the original. The customer's `total_payments`, `successful_payments` and
> `lifetime_value_paise` have all moved. The attempt row is `recovered` and carries the
> gateway payment id. `payment_verified` and `recovery_succeeded` close the ledger entries
> for this case.

**6. Prove it.**

```bash
curl "http://127.0.0.1:8000/api/audit?case_id=case_45af48a0f7a64c4a&limit=50"
curl http://127.0.0.1:8000/api/audit/verify
```

> *State:* unchanged. The first call is the case's complete life story, newest first; the
> second recomputes every hash from genesis and reports `valid: true`.

### The branches that are not the happy path

| Instead of step 3 | Call | Result |
|---|---|---|
| Decline it | `POST .../reject` | `rejected`, terminal, with the operator and reason in the ledger. |
| Customer never pays | `POST .../mark-failed` | `failed`, `expires_at` cleared, `failure_note` stating the remaining retry budget. |
| Try again after a failure | `POST /api/recovery/payments/{payment_id}/analyze` | Re-proposes onto the **same** case, preserving `attempt_count`. Within 15 minutes R2_COOLDOWN denies it and the case goes to `blocked`. |

## Notes that save time

**Money is always integer paise.** Fields ending `_paise` are the truth; the `_rupees`
sibling is a rounded convenience for display. Nothing in the system does arithmetic in
rupees, because `0.1 + 0.2 != 0.3` in binary floating point and a rounding error in a
payment system is a defect, not a curiosity. The recovery amount is copied from the original
payment and is never accepted from a request body — not from the agent, not from the
checkout callback.

**Timestamps are ISO-8601 UTC with a `Z`.** Values nested inside an audit `payload` are
opaque JSON written by the code that recorded the event and may appear as `+00:00`.

**Guardrails are re-evaluated on approve, so a `403 guardrail_denied` there is expected
behaviour.** A proposal is a snapshot of a world that keeps moving: between proposing and
approving, the daily budget gets spent down by other cases, the customer opens more cases,
the payment ages past the freshness window, an attempt accumulates. The binding check is the
one taken at the instant money would move. `detail.blocking_rules` names the rules that
fired — for example `["R8_CUSTOMER_VELOCITY"]` — and the case is moved to `blocked` and
committed *before* the error is raised, so a refused case never sits in the approval queue
pretending to be actionable.

**`simulate-checkout` only works against the simulated gateway.** With real Razorpay
credentials configured it raises `500 configuration_error` with
`detail.gateway_mode: "razorpay_test"`. The check is on the gateway that is actually wired
up, not on an environment name a deployment could get wrong: a demo shortcut that still
worked against a real gateway would be a way to mark real money collected without
collecting it.

**The two list filters behave differently on a bad value.** `GET /api/payments?status=` is a
closed literal and answers `422` for anything unrecognised; `GET /api/recovery/cases?status=`
is a free string matched against the stored column and answers `200 []`.

**`can_approve`, `can_reject` and `approval_blocked_reason` are computed on the server.**
Render them; do not re-derive them. They encode the state machine and the stored verdict
together, and a second implementation in the client is a second copy of the policy that will
drift.

**Analysis is idempotent per payment, not per call.** A second `analyze` on a payment whose
case is live or closed returns `409 duplicate_case` with the existing `case_id` in `detail`.
Only a case in `failed` is re-proposed, and it is re-proposed onto the same row so the
attempt budget carries forward — otherwise "max 2 attempts" would silently become "max 2
attempts per analysis".

**Approve is safe to double-click.** The attempt row is keyed on the deterministic
idempotency key `case_id:attempt_number`, so a retried request finishes the first one's work
rather than asking the gateway for a second order against the same money.

**Expiry is swept on read, not on a timer.** `expires_at` is set when an order is created,
and `RecoveryService.expire_stale_cases()` moves timed-out cases to `expired`. It is driven
from `GET /api/recovery/cases` and `GET /api/recovery/cases/{id}/checkout` rather than from a
background task, so a link expires the first time anyone looks at the queue or opens the
payment page.

That is a deliberate choice over a scheduler: it adds nothing that can fail in a project whose
premise is that it runs with nothing installed, and a case that expires while nobody is
watching has not yet affected anyone. The property that matters — the state a caller sees is
always current — holds either way. It does mean `expires_at` can be in the past for a case
nobody has read yet; the next read corrects it before returning.

**There is no authentication and no rate limiting.** The server binds to `127.0.0.1` by
default and is designed to be run locally by one person. `approved_by` is a recorded name,
not a verified identity — the audit trail is built to record whatever identity it is given,
so adding SSO later changes where that string comes from and nothing else. The reasoning is
D19 in `docs/08-DESIGN-DECISIONS.md`; it is stated as a limitation rather than pretended
away.
